# 资金行为研究系统：开发任务书与验收标准

日期：2026-11-02。用户已选择：**先用公开数据做原型，再评估 Level-2**。

## 一、用户要解决的问题

选定A股及几个小时、几天、几周的窗口，研究是否存在持续买入或卖出力量，估计可识别的执行规模，并比较建仓、吸筹、洗盘、拉升、出货等解释。

允许综合市场心理、历史案例、行情、订单特征、执行算法、公司公告和市场环境。分析必须区分可观测事实、统计推断和行为动机。

## 二、术语与输出层次

这些词不是互斥标签：

- 建仓：持仓增加的结果。真正确定需要投资者或账户层面信息。
- 吸筹：可能以低冲击、分批、被动承接等方式买入。
- 拉升：价格重心快速上移的可观测结果，背后可能有多种资金。
- 出货／派发：持仓减少的结果，可能伴随上升、横盘或下跌。
- 洗盘：包含“让其他持有人退出、随后继续上涨”等意图和后续结果。实时只能给“回撤承接／洗盘候选”；后验走势也不能独自证明动机。

每次分析输出三层：

1. 事实：时间覆盖、量价、平台订单分类、新闻发生时间、股东披露截止日。
2. 推断：持续买入压力、疑似执行风格、阶段候选及反向证据。
3. 尚不可识别：真实账户身份、真实机构净持仓变化、无法校准的母单金额。

## 三、第一版实际范围

已建立 `flowradar` Python模块和命令行工具，生成可本地打开的交互式HTML、Markdown、JSON报告。

公开数据原型实现：行情与资金分类适配器、单位统一、区间过滤、相对强弱、量价特征、阶段候选、质量报告、离线复算和滚动价格结果观察。

第一版阶段引擎是**透明规则基线**。不把规则分数称为置信概率，不声称它已经识别主力。

## 四、数据层设计

统一使用北京时间。价格单位元，成交量单位股，成交额和资金净额单位元。

| 数据 | 可支持的研究 | 当前局限 |
|---|---|---|
| 日线OHLCV | 多日多周趋势、量价、相对强弱 | 无法识别分钟级执行；当前未复权 |
| 分钟行情 | 小时级承接、价格重心、成交节奏 | 无原始订单编号和账户身份 |
| 平台大小单净额 | 订单分档行为的辅助证据 | 分类口径不等于真实投资者类型 |
| 公开成交明细 | 时间格点诊断、粗粒度成交观察 | 可能聚合或采样；不等于完整逐笔 |
| Level-2逐笔委托和成交 | 委托还原、挂撤单生命周期、候选订单簇 | 通常仍无最终投资者母单标识 |
| 真实执行标签 | 训练与校准母单识别和金额估计 | 当前没有；需合法取得 |
| 公告、调研和持股披露 | 事件和参与者动机背景 | 披露有延迟，不得当成实时持仓 |

每个响应保留URL、参数、取得时间及原始缓存。失败回退必须披露，不偷偷补造数据。不同源的数据差异需要保留。

分钟累计量额、累计分类净额必须**先按交易日求增量，再切分析窗口**。午休不得重复计算上午成交，负的分类净额变化可以合法出现，累计成交量回退则需要报错。

分析历史日期时，基准、成交量基线、新闻和标签必须符合当时可获得的信息集，不能借用未来数据。

## 五、模型升级路线

### 1. 价格与成交量基线

相对基准强弱、路径效率、收盘位置、回撤、价格区间成交、VWAP偏离、相同交易时刻的历史量比。

价格区间上涨成交占比不等于主动买入占比，更不等于机构买入占比。

### 2. 执行算法反演

同时比较随机TWAP、VWAP、POV、限价执行、动态追赶，以及“没有单一大买家”的对照。

拟合对象应是候选交易序列，不能把整只股票成交量或全部小单净额直接当作某个母单执行轨迹。

可估计的参数包括启动／结束时段、参与率、价格约束和随机程度；母单金额只在识别条件与误差验证足够时给区间。

采用先前时段识别、后续时段验证，允许算法混合与策略切换。拒绝事后任意选择区间直至看起来像吸筹。

### 3. 隐藏状态与多周期融合

研究HMM／HSMM的持续买入、卖出、混合交易状态；研究变点检测区分执行启动、加速和终止。

小时级执行状态与日／周级趋势分别建模，再融合。日线趋势不能直接代替账户净持仓。

### 4. 挂撤单行为特征

包括委托存续时间、撤单分布、成交后补单、买卖侧差异和参与率。识别程序化参与度不等于识别知情资金或净建仓。

供应商采样周期、行情发布时间和数据截断必须先诊断，再考虑算法周期。

### 5. 历史案例与心理情景

每个案例保存证券、时间窗口、来源、当时可知信息、后续披露、标签来源和不确定性。

把“监管查明的账户行为”“匿名真实执行样本”“模拟注入母单”“仅事后走势像某种形态”分开管理，不能混为真实标签。

心理和博弈层可以提出主动增仓、被动赎回、跟随指数、追涨、回补、反弹减仓等竞争解释。新闻或大模型生成的叙事不能覆盖数据反证。

## 六、金额估计必须分清的口径

1. 区间市场成交额：数据充分时可以观测。
2. 平台某订单分档的净额：有口径限制的观测。
3. 候选算法执行金额：依赖识别方法的估计。
4. 特定机构净增持金额：需要身份、净头寸或经独立验证的估计模型。

当前公开数据版只输出前两层。后两层缺失时为null，不能填0，也不能填一个看起来精确的区间。

未来提供金额区间，须同时说明买入总额或净额、是否包含回补、估计模型、误差校准样本和区间覆盖率。

## 七、评估与验收

- 单位和累计值处理正确，午休与多日窗口不重复计量。
- 明确请求区间、实际覆盖区间、源数据粒度和缺失项。
- 任何时点的特征只能使用该时点及之前数据。
- 阶段分数先作为规则分数；经验证后才能显示概率和校准曲线。
- 真正的算法识别：用已知执行标签报告精确率、召回率和误报，按股票和日期分组留出。
- 模拟数据检验灵敏度与鲁棒性，不代替真实市场准确率。
- 金额估计：报告误差分布和区间覆盖率，不能只报告均方误差。
- 后续上涨胜率不等于识别主力准确率；撤单因子的IC也不等于账户识别准确率。
- 检查指数上涨、热门题材跟随、低流动性、集合竞价、停牌、除权、数据丢失、做T及被动调仓等混淆。
- 分开报告交易层识别、后续走势预测、真实账户状态验证三个任务。
- 回测应包含滚动验证、重叠样本处理、交易成本与幸存者偏差；不能凭某一只股票某一天校准系统。

## 八、AI在开发和软件中的职责

开发建议：GPT-6 Astra配合High或Extra High，承担方法设计、复杂实现和评估审查；持续迭代可用GPT-6.1 Sol。具体以用户可选模型为准。

软件内部数值引擎应可复算。大模型可用于公告抽取、案例归纳、竞争情景解释和报告表达；不允许通过自由文本补造交易金额或置信概率。

这一版本未接任何付费模型API，运行不需要OpenAI密钥。

## 十、继续开发时的工作顺序

1. 复核现有原型输出和源数据质量，扩大公开日线／分钟历史覆盖。
2. 建立可长期保存的原始数据版本及公司行为处理。
3. 接入经授权的逐笔委托和成交，完成订单还原与采样诊断。
4. 加入合成执行场景，覆盖随机TWAP、VWAP、POV、限价和混合执行。
5. 在独立真实样本上验证隐藏订单识别，随后才启用金额区间。
6. 引入案例库和可追溯事件分析，最后融合多周期输出。

后续开发应保留当前“不知道就不输出金额”的约束，不能为了界面完整把不可识别字段自动补齐。
